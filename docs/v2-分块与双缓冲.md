# v2 · 分块搬运与双缓冲

> 提交：`v2-chunk` → `v2-pingpong` ｜ 代码：`versions/matmul_v2_chunk.cpp`、`versions/matmul_v2_pingpong.cpp`
> diff：`docs/patches/02_v1_to_v2chunk.diff`、`docs/patches/03_v2chunk_to_v2pingpong.diff`
> 单元：Vector，40 核

这一版拆成两步做，因为它们是两个独立的问题。

## 第一步（v2-chunk）：把搬运粒度从 2 KB 放大到 32 KB

### 判断依据

v0/v1 的诊断显示 MTE2 的**活跃带宽只有 14.8 GB/s**，但 40 核的扩展效率却有 95%——如果是带宽不够，不可能有这么好的线性扩展。所以不是带宽问题，而是**单次搬运太小，固定延迟摊不掉**。

用两组数据反解延迟模型：

```
2 KB  → 129 ns = L + 2048/BW
```

### 改动

```cpp
constexpr uint32_t Kb = 16;              // 一次搬 16 行 B
constexpr uint32_t NK_BLOCK = K / Kb;    // 64 个 K 块

DataCopy(bBuf, bGm[kb * Kb * N], Kb * N);   // 2 KB → 32 KB
```

内层计算不变，只是外层多了一层 K 分块。**同步结构与 v0 完全一致**（`SetFlag` 紧跟配对的 `WaitFlag`），不引入新风险。

### 结果

| 指标 | v1 | v2-chunk |
|---|---|---|
| 耗时 | 5.3919 ms | **2.4663 ms** |
| 算力 | 0.3983 | **0.8707 TFLOPS** |
| MTE2 活跃带宽 | 14.8 GB/s | **104.5 GB/s（7.1×）** |

## 第二步（v2-pingpong）：双缓冲，让搬运与计算重叠

### 判断依据

v2-chunk 之后 `vec + mte2` 的时间占比仍是 **95.4%**——两条流水线在时间上互斥，说明还是串行。Cube/Vector 只占 33%，MTE2 占 62%，**两者的时间加起来正好铺满**。

### 改动：预取 2 块 + 自己回填自己

```cpp
// 预取前两块
DataCopy(bBuf0, bGm[0],         Kb * N);  SetFlag<MTE2_V>(EVENT_ID0);
DataCopy(bBuf1, bGm[Kb * N],    Kb * N);  SetFlag<MTE2_V>(EVENT_ID1);

for (kb = 0; kb < NK_BLOCK; ++kb) {
    cur = kb & 1;
    WaitFlag<MTE2_V>(cur);                 // 等当前块
    compute(bBuf[cur]);                    // 算它
    SetFlag<V_MTE2>(cur);                  // 释放它
    if (kb + 2 < NK_BLOCK) {
        WaitFlag<V_MTE2>(cur);             // ← 立即等自己刚释放的
        DataCopy(bBuf[cur], chunk(kb+2));  // 填回同一块
        SetFlag<MTE2_V>(cur);
    }
}
```

**关键设计**：回填的是「刚算完的那块」，所以 `WaitFlag<V_MTE2>` 永远紧跟在自己的 `SetFlag` 后面，同一指令流内成对出现——不存在「等上一轮设下的旗标」这种跨迭代依赖。

### 两个踩过的坑

**坑 1：第一版直接死锁（`timeout` 返回 124）**

初版把 `WaitFlag<V_MTE2>` 放在迭代顶部、等的是**上一轮**的释放旗标。诊断方法：把 `Kb` 从 16 改回 1（2 KB，v0 已验证可用）**仍然死锁** → 一步排除「32 KB 搬运超限」，把范围锁死在旗标逻辑上。

**坑 2：加了双缓冲后 40 核反而慢 1.6 倍（3996 µs vs 1997 µs）**

工具链把算子误判成了 **mix 核**（每块 1 AIC + 2 AIV），`blockDim=40` 实际启动 **80 个 AIV 任务压到 40 个物理核**上跑两波。诊断线索：`msprof` 里 `Op Type: mix`、`核数 120`，以及 `build/auto_gen/.../aiv_config.cmake` 里的 `MIX_SOURCES`。

修复只要一行：

```cpp
KERNEL_TASK_TYPE_DEFAULT(KERNEL_TYPE_AIV_ONLY);
```

**如果按表象回退双缓冲，会得出「双缓冲有害」的错误结论。**

### 结果

| 指标 | v2-chunk | v2-pingpong |
|---|---|---|
| 耗时 | 2.4663 ms | **1.9973 ms** |
| 算力 | 0.8707 | **1.0752 TFLOPS** |
| `vec + mte2` 占比 | 95.4%（串行） | **114.6%（已重叠）** |
| MTE2 绝对时间 | 3435 µs | **486 µs** |
| 负载不均 | — | 4.12% |

## 验证过但没采用的一档：`Kb = 32`

顺手做了一次假设检验：把单次搬运从 32 KB 加到 64 KB。

| 指标 | `Kb=16` | `Kb=32` |
|---|---|---|
| MTE2 时间 | 486 µs | **346 µs**（确实降了） |
| 总时长 | 1997 µs | **2008 µs（没变）** |
| UB 占用 | 80 KB | 144 KB |

**MTE2 改善了，总时长没变** —— 因为它已经被完全掩盖在 Vector 时间后面。这个实验确立了一条判断准则：

> 当 `MTE2 时间 < Vector 时间` 时，继续优化搬运的收益**确定为 0**，不用试也不用猜。

## 这一版没解决的问题

- **Vector 仍是唯一瓶颈**（占 90.3%），且每 k 步要做 3 条向量指令
- 负载不均 4.12%，已等于行切分的数学下界，不可再降
- L1 利用率仍只有 12.5%（每块搬进来只用一次）
