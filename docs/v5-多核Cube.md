# v5 · 多核 Cube（kernel 内自行切分）

> 提交：`v5-multicore` ｜ 代码：`versions/matmul_v5_multicore.cpp` ｜ diff：`docs/patches/06_v4_to_v5multicore.diff`
> 单元：Cube（AIC），**16 核**

## 1. 判断依据

v4 单核 msprof：`MTE2 93.1%` 已饱和。**MTE2 是核内独占资源**，所以再怎么调 tile 尺寸、调 L1 深度都没用——只有加核才能分摊。

而 host 侧的 `MatmulApiTiling` 在本 CANN 版本无法指定核数（见 v4 文档第 5 节）。于是把核间切分搬到 kernel 里。

## 2. 改动

关键发现：`MatmulImplBase` 提供**运行期**的 `SetOrgShape` / `SetSingleShape`（`matmul_impl_base.h:99-101`），所以 tiling 按单核生成也没关系，kernel 可以声明"我只算这一块"。

```cpp
const uint32_t blk = AscendC::GetBlockIdx();
const uint32_t mt  = blk / 4;          // 4×4 网格
const uint32_t nt  = blk % 4;

mm.SetOrgShape(M, N, K);               // 原始矩阵
mm.SetSingleShape(tileM, tileN, K);    // 本核计算量
mm.SetTensorA(aGm[mt * tileM * K]);    // A 的第 mt 个 M 带
mm.SetTensorB(bGm[nt * tileN]);        // B 的第 nt 个 N 带
mm.IterateAll(cGm[mt * tileM * N + nt * tileN]);
```

## 3. 为什么是 16 核而不是 20 核

910B3 有 20 个 AIC，但：

```
M/N = 1024 = 2¹⁰ ，核数 = 20 = 4×5
Cube 要求每维 16 元素对齐
1024/5 = 204.8  →  不是 16 的倍数，5 路切分无法均分
```

而固定 tile 尺寸时的对比更能说明问题：

```
20 核：64 块 → 4 核拿 4 块、16 核拿 3 块
      关键路径 4 块 → 有效吞吐 = 64/4 = 16 核当量
16 核：64 块 → 每核正好 4 块 → 同样是 16 核当量
```

**两者等效吞吐相同**，但 16 核零失配更简单、调度开销更小。实测负载不均仅 **4.65%**。

## 5. 三个被数据推翻的判断（这一版最大的收获）

### ① 「MTE2 是带宽受限」——错，是延迟受限

`docs/prof/v5-multicore-L2Memory/`：

| 指标 | 数值 | 含义 |
|---|---|---|
| GM→L1 带宽利用率 | **18.38%** | MTE2 占空 61% 却只用 18% 带宽 |
| L1 读带宽 | 50.6 GB/s | 片上带宽远未饱和 |
| L2 读命中率 | **75.78%** | 复用大部分被 L2 吸收 |

**占空比高 + 带宽利用率低 = 在等每一条搬运完成，不是塞满了管道。**

### ② 「4096³ 撞带宽墙」——错

把 tile 从固定 256 改成固定 4×4 网格（tile = M/4），复用放大从 `N/256` 降到恒定的 4×：

| 尺寸 | 流量变化 | 算力变化 |
|---|---|---|
| 1024³ | 16 MB（不变） | 85.996 → 87.674（+1.9%） |
| 2048³ | 128 → 64 MB | 146.692 → 150.696（+2.7%） |
| 4096³ | **1 GB → 256 MB** | 168.417 → 172.809（**+2.6%**） |

**流量减 4 倍，只换来 2.6%** —— 4096³ 实测只有 322 GB/s，远未到 HBM 峰值。此前"大尺寸被带宽卡住"的推断是错的。

### ③ 「L0C 双缓冲能提升」——负收益

`SetFixSplit(128,128,64) + SetDoubleBuffer(T,T,T,F)`（让 Fixpipe 与 Mmad 重叠）实测 **78.14 TFLOPS**，低于 auto 的 **88.10**。因为把 `baseN` 从 256 砍到 128 后，Cube 每次干活变少、指令数变多，损失大于重叠收益。

## 6. 与官方实现的差距，以及为什么

`scripts/bench_official.py`（`torch_npu` → `aclnnMatmul`）同口径实测：

| 尺寸 | 官方 | 本项目 | 对比 | 占 16 核可达* |
|---|---|---|---|---|
| 1024³ | 69.30 | **87.67** | **1.26×** | 37.2% |
| 2048³ | 230.38 | 150.70 | 0.65× | 63.9% |
| 4096³ | 273.16 | 172.81 | 0.63× | **73.2%** |

\* 16 核可达 = `294.9 × 16/20 = 235.9 TFLOPS`

差距分解（4096³）：

```
172.81 = 294.9 × (16/20) × 0.732
                    ↑核数    ↑单核效率
```

| 损失来源 | 量级 | 能否解决 |
|---|---|---|
| 只用 16/20 个核 | 约 43 TFLOPS | 受 16 对齐硬约束 |
| 单核效率 73%（官方 92.6%） | 约 46 TFLOPS | 属 API 内部调度，可调项已扫尽 |

## 7. 这一版仍未解决

- 16/20 核的上限（16 元素对齐，5 路切分除不尽）
- 单核 73% 效率距官方的 92.6% 还有约 19 个百分点
- kernel 只支持 M/N 为 4 的倍数，未做尾块处理
- 手写 Mmad 路线：20 核时 `repeat=100` 实测 **41.5 TFLOPS**（0.0517 ms），**低于当前 API 版 16 核的 88.3 TFLOPS**；
  且其 `Fixpipe` 未修通（输出只写入 6.2%、`fro_err=NaN`）。
  **所以"手写路线潜力更大"这个说法缺乏数据支撑** —— 修通它的 `Fixpipe` 并不代表能超过 API 版，
  真要验证必须先修通再同口径复测。
